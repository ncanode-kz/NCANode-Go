# Инструкции для агентов

## Сборка требует нативный SDK - его нельзя скачать автоматически

Проект использует [gokalkan](https://github.com/ncanode-kz/gokalkan) - обёртку
над нативной библиотекой **KalkanCrypt** (`libkalkancryptwr-64.so`). Без неё
`go build`/`go test` не соберутся (CGO-зависимость).

SDK не лежит в открытом доступе - его нужно запросить у **[pki.gov.kz](https://pki.gov.kz/developers/)**.
Это ручной шаг: если библиотека не установлена в окружении, попроси
пользователя предоставить её (`.so`-файл + CA-сертификаты для установки) -
самостоятельно её раздобыть агент не может.

## Только x86_64 - на ARM не работает

`libkalkancryptwr-64.so` скомпилирована KalkanCrypt только под **x86/x86_64**.
На ARM (в т.ч. Apple Silicon, ARM-серверы, `GOARCH=arm64`) библиотека не
загрузится - проект в принципе не соберётся и не запустится на этой
архитектуре. Не трать время на отладку "непонятных" ошибок cgo/dlopen на ARM -
это ожидаемо, единственное решение - x86_64-окружение (в т.ч. эмуляция/VM).

## OID Республики Казахстан

Все специфичные для казахстанской PKI OID (алгоритмы подписи, типы
сертификатов, поля subject/issuer и т.д.) можно посмотреть в официальном
реестре: **https://root.gov.kz/oid/**. Используй его, если встретился
незнакомый OID (например, при расширении `certservice.signAlgByOID` или
разборе полей сертификата) - не гадай и не выдумывай названия.

## Oracle-тесты сверяются с Java-версией

Эталонная реализация NCANode (Java), с которой этот порт должен быть 100%
совместим по HTTP API, лежит здесь: **https://github.com/ncanode-kz/NCANode**.

Interop-тесты за `//go:build oracle` (см. `internal/service/*/oracle_test.go`)
поднимают эту Java-версию локально и сверяют ответы в обе стороны (Go
подписывает → Java проверяет, и наоборот). Команды сборки/запуска и нужные
тестовые URL (`test.pki.gov.kz`) - см. `## Тесты` в README.md и
`gokalkan/internal/oracle/README.md`. Если меняешь поведение эндпоинта -
запускай `go test -tags oracle ./...` против живого Java-сервиса, прежде чем
считать изменение завершённым.

## При изменении HTTP-методов - обновляй Swagger

`internal/openapi/openapi.json` - это не сгенерированный файл, а ручная копия
контракта. Он должен оставаться 1:1 синхронным с `internal/dto` и
зарегистрированными роутами (`RegisterRoutes` в каждом `internal/service/*`).

Если ты добавляешь/удаляешь эндпоинт, меняешь поля запроса/ответа
(включая имена, типы, обязательность, enum-значения) или добавляешь нового
подписанта/параметр - **обнови соответствующий `paths`/`components.schemas`
блок в `openapi.json`** в том же коммите. Расхождение между реальным API и
свагером - это баг, а не мелочь: сервис существует именно ради 100%
совместимости по контракту с Java-версией.

После правки проверь, что спека остаётся валидным JSON и сервис её
по-прежнему отдаёт:

```sh
go run ./cmd/ncanode &
curl -s http://localhost:14579/v3/api-docs | python3 -m json.tool > /dev/null && echo OK
```
